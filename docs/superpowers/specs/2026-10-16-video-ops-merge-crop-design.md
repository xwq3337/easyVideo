# EasyDownVideo · 视频操作（其三）· 合并与画面裁剪设计

- 日期：2026-10-16
- 状态：待评审
- 前置：`docs/superpowers/specs/2026-10-16-video-ops-design.md`（子系统与压缩）、
  `docs/superpowers/specs/2026-10-16-video-ops-transcode-trim-design.md`（泛化、转码、裁剪）
- 定位：补齐视频操作的最后两个。含一次**输入模型的泛化**（单文件 → 多文件）

## 1. 背景与目标

「视频操作」现在五个入口里三个可用（压缩、转码、裁剪视频），合并与画面裁剪仍灰显。
本轮把这两个做完，五个全通。

**目标**：
- **合并**：把 N 个视频按指定顺序拼成一个。
- **画面裁剪**：截取画面的一个局部（改画面尺寸），**时长不变**。

**成功标准**：三段同规格的视频能拼成一个能播的文件；编码不一致时**拦住并说清**；
裁剪框能看着预览图定，裁出来的时长与源**完全相同**。

## 2. 家底与实测结论

前两轮的结论仍然有效（内嵌 ffmpeg 9.0.2、没有 ffprobe、`out_time_ms` 也是微秒、
VideoToolbox 静默忽略 `-crf`、容器与编码器不是自由组合、`-c copy` 裁剪切口是准的）。
本轮新增六条，全部实测：

**合并：编码不一致时 `-c copy` 会产出坏文件，而 ffmpeg 报 exit 0。**

| 组合 | ffmpeg exit | 产物解码错误 |
|---|---|---|
| 三段同规格 | 0 | **0** ✓ |
| 分辨率不同（编码相同） | 0 | **0** ✓ |
| 帧率不同 30 + 25 | 0 | **2 行**（接缝处一跳） |
| 音频参数不同（44.1k 立体声 + 48k 单声道） | 0 | 0 ✓，但总时长偏 **+0.36 秒** |
| 一段无音轨 + 一段有 | 0 | **0** ✓ |
| **h264 + h265** | 0 | **3 行** ✗ |
| **h264 + mpeg4** | 0 | **174 行** ✗ |

所以"编码是否一致"必须**我们主动检查** —— ffmpeg 不会报错。

**画面裁剪：越界与奇数尺寸都会被静默改掉，且 stderr 里一条警告都没有。**

```
源 1920x1080：
  请求 crop=641:360          → 实际 640x360      （奇数被静默取偶）
  请求 crop=640:361          → 实际 640x360
  请求 crop=1280:720@x=1200  → 实际 1280x720     （1200+1280=2480 已超出 1920，x 被静默钳到 640）
```

第三条最要命：用户要的是画面右侧那一块，拿到的是**完全另一个位置**的一块，而命令行
退出码是 0、stderr 是空的。所以裁剪框的合法性必须由我们判定，不能指望 ffmpeg 报错。

**裁剪不改时长。** 源 3.00 秒 → `crop=640:360` 产物仍是 3.00 秒、尺寸 640x360。
「画面裁剪」与「裁剪视频」是两件事，这条实测把它们划清。

**抽帧预览可以走 data URL。** 一帧缩到 640 宽、JPEG 质量 5 = **13.7 KB**，base64 后
18 KB —— 过 IPC 毫无压力。（`tauri.conf.json` 里**没有开** `assetProtocol`，所以不走
文件协议是对的，不必为它加配置与权限。）

**`MediaInfo` 目前没有画面尺寸。** 裁剪框的坐标系就是源宽高，必须加。
尺寸能从 `Stream #0:0…, yuv420p(progressive), 1920x1080 [SAR…` 那行解析。

**方法学**：写 zsh 临时脚本时 `$2:rate` 会被当成参数修饰符（`$2:r` + `ate`），
要用 `${2}:rate`。这一条让本轮的一次实测白跑了一轮 —— 而**报错信息看上去像是 ffmpeg
的参数错了**（"Unable to parse size option value 640x360ate=30"），方向完全指错。
用 bash 或加花括号。

## 3. 范围

**本轮做**：输入模型泛化（多文件）、合并（含兼容性检查与拒绝）、画面裁剪（含抽帧预览）、
两个命令（`check_merge` / `preview_frame`）、两个表单。

做完之后 `VIDEO_OPS` 五项全部 `ready: true`，侧边栏不再有灰显项 —— **那条"不做假按钮"
的守卫测试要跟着改成"五项全都 ready"**，而不是删掉。

**不做**：见第 12 节。

## 4. 引擎结构变化

### 4.1 输入从单个变成一组

```rust
// 之前
pub async fn add_job(&self, input: PathBuf, output_dir: PathBuf, params: JobParams) -> Result<JobId>
// 之后
pub async fn add_job(&self, inputs: Vec<PathBuf>, output_dir: PathBuf, params: JobParams) -> Result<JobId>
```

`JobEntry.input` → `inputs: Vec<PathBuf>`；`JobSnapshot.inputs`；DTO 里是 `inputs: string[]`。
现有三个操作各传一个元素的 vec，**行为不变**。

理由不是"合并需要多个"，而是**参数与输入该分开**：`JobParams` 说"怎么处理"，`inputs`
说"处理什么"。合并的参数其实一个都没有（顺序就是 inputs 的顺序）。

### 4.2 五个能力改收一个 `JobContext`

合并会逼出这件事：它的 `args` 需要**全部**输入（拼 concat 列表）、`validate` 需要**每一段**
的媒体信息（比编码），而现在的签名只收一个 `src: &MediaInfo`。

```rust
pub struct JobContext<'a> {
    pub inputs: &'a [PathBuf],
    /// 与 `inputs` 一一对应。合并的兼容性校验要逐段看。
    pub infos: &'a [MediaInfo],
    pub output: &'a Path,
    /// 本次任务要写的临时文件（合并的 concat 列表）。由 `run_job` 负责清理。
    pub scratch: Option<&'a Path>,
}

impl JobContext<'_> {
    /// 首段的媒体信息。单输入的操作看的就是它。
    pub fn src(&self) -> &MediaInfo { &self.infos[0] }
}
```

五个能力随之变成：

```rust
impl JobParams {
    pub fn label(&self) -> String;
    pub fn suffix(&self) -> &'static str;
    pub fn extension(&self, ctx: &JobContext) -> String;
    pub fn args(&self, ctx: &JobContext) -> Vec<String>;
    pub fn validate(&self, ctx: &JobContext) -> anyhow::Result<()>;
}
```

压缩/转码/裁剪把 `src` 换成 `ctx.src()`，**行为一字不改** —— 它们仍然只看首段。

### 4.3 临时文件的归属

合并要一个 concat 列表文件。它：

- 由**调用方在 `add_job` 里算好内容**（`merge::concat_list(inputs)` 是纯函数），
  存进 `JobEntry`；
- 路径在**应用数据目录**（`<data_dir>/merge-<id>.txt`）—— 那是我们自己的地盘，
  不往用户的输出目录里丢东西；
- 由 **worker 在跑之前写**（排队中被取消的任务从没写过它，没有可清理的）；
- 由 **`run_job` 在成功/失败/取消时删掉** —— 它已经负责 `.part` 的清理了，
  "这次任务用过的临时文件"是同一份责任，不该散到第二个地方。

于是 `run_job` 多一个参数：`scratch: Option<&Path>`。

## 5. 合并的行为

### 5.1 输入与顺序

对话框多选（`pick_files`）→ 列表，每行显示文件名与媒体信息摘要，带**上下移动**按钮。
顺序就是拼接顺序，界面上写清「按此顺序拼接」。不做拖拽排序。

### 5.2 兼容性检查

`merge::check(infos) -> MergeCheck { blockers, warnings }`，纯函数；配一条 `check_merge`
命令让界面调用。**规则只写在 core 一处** —— 前端不重抄一份（抄两份必然漂移，
时间解析那边已经吃过一次亏）。

| | 判据 | 依据（第 2 节的实测） |
|---|---|---|
| **blockers** | 视频编码不一致 | h264+h265 → 3 行解码错误；h264+mpeg4 → 174 行 |
| | 音频编码不一致（**只比有音轨的那些段之间** —— 有的段压根没音轨不算不一致，见下面的 warning） | 同上（同源） |
| **warnings** | 分辨率不同 | 0 错误，但接缝处画面尺寸会变 |
| | 帧率不同 | 2 行错误 —— 接缝处会一跳 |
| | 音频参数不同（采样率/声道） | 0 错误，但总时长会偏 |
| | 有的段没有音轨 | 0 错误，但拼出来的音轨是断的 |

存在 blocker 时**开始按钮禁用**，并把理由显示出来。文案要**指路**：

> 无法合并：第 2 段的视频编码是 hevc，与第 1 段（h264）不一致。
> 直接拼接会产出一个打不开的文件。可以先把它「转码」成 MP4 · H.264 + AAC，再回来合并。

复用已有的「转码」而不是替用户默默重编一遍 —— 后者会让"合并"变成一个慢得多、
还有损的操作，而用户点的是"合并"。

### 5.3 命令行与容器

```
-f concat -safe 0 -i <列表文件> -c copy -f <muxer> <产物>
```

- **列表的转义必须复用 `hls::escape_concat_path`** —— 上一轮为"下载目录里带撇号"
  踩过一次，那一次是**每一次 HLS 下载都在最后合并这步失败**。同一个坑不许踩第二次。
- muxer 沿用**首段**的容器；认不出来退 `matroska`（什么都装得下）—— 与裁剪的快速档
  同一套规则、同一个 `container_muxer`。这个退化会体现在产物名预览里。
- 产物名 `<首段原名>-合并.<ext>`；重名照旧让路成 ` (1)`。

### 5.4 进度

合并的 `duration_secs` 是**各段之和**（concat 的产物时长就是它们相加）。不这么做的话
进度条会在第一段结束时就走满。

## 6. 画面裁剪的行为

### 6.1 参数与命令行

```rust
pub struct CropParams { pub width: u32, pub height: u32, pub x: u32, pub y: u32, pub preset: CompressPreset }
```

```
-vf crop=<w>:<h>:<x>:<y>  +  -c:v libx264 -crf <档位> -c:a aac -f mp4
```

容器固定 mp4 —— **重编码的操作输出 mp4** 是这个 App 既有的约定（压缩页、裁剪的精确档
都是这样），不为裁剪开第二个例外。预览里显示扩展名。

### 6.2 合法性由我们判定

| 规则 | 不校验会怎样（第 2 节实测） |
|---|---|
| 宽、高都必须是**偶数**且 ≥ 2 | 请求 641 得到 640，**没有任何提示** |
| `x + 宽 ≤ 源宽`、`y + 高 ≤ 源高` | 请求 x=1200 得到 x=640 —— 完全是另一个位置 |

`validate` 里逐条判，错误信息带上源尺寸（"宽 1280 + 左 1200 超出了画面的宽度 1920"）。

**界面上还要让非法状态难以进入**：宽高输入按 2 递增、上限是源尺寸；改宽高时把左/上
**可见地**钳到新上限（数字当场变）。这里与 ffmpeg 的区别正是"可见"——它悄悄钳、
用户不知道；我们钳了，用户看得见那几个数字变了。

### 6.3 时长不变

`-vf crop` 不碰时间戳，时长天然不变。但这是本轮**验收的硬指标**，所以写成断言：
端到端测试里比较源与产物的**时长相等**、**帧数相等**。将来有人往这里加 `-ss`/`-to`
或换滤镜时，这条会立刻红。

### 6.4 抽帧预览

新增命令：`preview_frame(path: String, at_secs: f64) -> Result<String>`，返回
`data:image/jpeg;base64,…`。实现是：

```
ffmpeg -ss <at_secs> -i <path> -frames:v 1 -vf scale=640:-2 -c:v mjpeg -q:v 5 -f image2 -
```

默认取视频 **10%** 处（避开开头的黑场/台标；**时长读不出来时取 0 秒**，也就是首帧），
旁边给一个时间输入可以换时间。这个 10% 由表单自己算（它已经从 probe 拿到了时长）。
裁剪是静态的，所以一帧够用 —— 不做时间轴上的拖拽预览。

叠加框按 `源宽 / 预览宽` 缩放绘制（就一次乘法）。**框画的是"校验通过之后"
的矩形**：数字非法时不画框、只显示错误，而不是画一个越界的框。

### 6.5 需要 `MediaInfo` 加宽高

```rust
pub struct MediaInfo { …, pub width: Option<u32>, pub height: Option<u32> }
```

从 `Stream #0:0…: Video: h264 …, yuv420p(progressive), 1920x1080 [SAR…` 那行取。
取不到时 `None` —— 裁剪页据此显示"读不出画面尺寸，无法裁剪"并禁用开始按钮，
而不是拿 0 去算。

## 7. 命令面与前端

### 7.1 命令变化

| 命令 | 变化 |
|---|---|
| `add_video_job` | `input: String` → `inputs: Vec<String>` |
| `plan_output` | 同上 |
| `check_merge` | **新增**：`(inputs: Vec<String>) -> MergeCheckDto` |
| `preview_frame` | **新增**：`(path: String, at_secs: f64) -> String`（data URL） |

`JobParamsDto` 加两个变体：`{op:"merge"}`（无参数）、`{op:"crop", width, height, x, y, preset}`。
`VideoInfoDto` 加 `width` / `height`。

### 7.2 前端

外框（`VideoOpShell`）现在要处理**多文件**：`input: string | null` → `inputs: string[]`。
单文件的操作仍然只放一个（选择按钮把列表替换成一个）。

- `MergeForm`：文件列表（上下移、删除）+ 兼容性结果（blockers 红字、warnings 灰字）
- `CropForm`：预览图 + 叠加框 + 四个数字输入 + 时间输入 + 质量档位

两个表单沿用既有的 `{ value, onChange }` 契约（`value` 为 `null` 表示参数还不合法，
外框据此禁用开始按钮）。**判断逻辑照旧提到 `opForms.ts` 那类纯模块里配测试** ——
这一轮的判断（兼容性、裁剪框钳制、奇数取偶）比上一轮更多，更不该埋在组件里。

预览的取帧命令在**文件或时间变化时**调用（`preview_frame` 要跑一次 ffmpeg），
与产物名预览同一套"只在影响它的东西变化时重算"的做法（`planKey` 已有先例）。

`VIDEO_OPS` 五项全 `ready: true`；那条守卫测试改成断言"五项全都 ready，没有灰显项"。

## 8. 错误处理

沿用前两轮的全部规则（入队校验、失败删半截产物、改名失败也清理、stderr 取尾部）。
本轮新增：

- **合并的 blocker 在入队时也要再判一次**（界面已经拦过，但 DTO 是外部输入）。
- **裁剪越界/奇数在入队时拒绝**，不依赖 ffmpeg 的静默钳制。
- **预览抽帧失败**（文件读不了、时间超出时长）→ 返回错误让界面显示一行"取预览失败"，
  **不阻断裁剪本身**（用户仍然可以填数字提交）。

## 9. 测试策略

| 层 | 内容 |
|---|---|
| `merge::concat_list` | 单段、多段、**路径含撇号/空格/中文**（转义的回归测试）、空输入 |
| `merge::check` | 编码一致 → 无 blocker；h264+h265 → blocker；分辨率/帧率/音频不同 → warning；无音轨混合 → warning |
| `merge::merge_args` | `-f concat -safe 0 -i <列表> -c copy`、显式 `-f`、输出在最后、`.part` 结尾 |
| `merge` 的容器选择 | 首段是 mkv → `-f matroska`；首段认不出来 → 退 matroska |
| **端到端真跑（合并）** | 三段同规格 → 拼成一个，**时长≈三段之和**、能解码、帧数≈之和 |
| **端到端真跑（合并拒绝）** | 造一段 h265，与 h264 一起交给 `check` → **必须报 blocker**（这条守的是第 2 节那 174 行解码错误） |
| `crop` 的参数与校验 | `crop=<w>:<h>:<x>:<y>` 的形状；奇数宽 → 拒；越界 x → 拒；宽高 < 2 → 拒；合法值 → 通过 |
| **端到端真跑（裁剪）** | 真裁一次：尺寸是请求的那个、**时长与源相等**、**帧数与源相等**、能解码 |
| 列表文件的清理 | 成功与取消之后 `<data_dir>/merge-<id>.txt` 都不在了 |
| `MediaInfo` 的宽高 | 从真实 stderr 片段解析；取不到时 `None` 不 panic |
| 前端 | `opForms.ts` 那类纯逻辑照旧配 vitest；`VIDEO_OPS` 的五 ready 守卫 |

端到端那几条都**不需要网络**（素材现造、ffmpeg 内嵌），能进常规套件。

## 10. 验收清单（手动，逐项过）

1. 侧边栏五项**全部不再灰显**，五个都能进。
2. 合并页：能多选文件、能上下移动、顺序就是拼接顺序。
3. 三段同规格 → 拼成一个、能播、时长≈三段之和。
4. **h264 + h265 一起选 → 开始按钮禁用，并指出是第几段的哪个编码不一致、建议先去转码。**
5. 分辨率不同的两段 → 能拼，但有一条灰字警告。
6. 裁剪页：选文件后自动出现预览帧；改四个数字时框实时跟着变。
7. 裁出的**尺寸**是填的那个；**时长与源完全一致**（对着秒数看）。
8. 宽填奇数 → 输入框自己变成偶数（可见）；左+宽越界 → 左被**看得见地**钳到上限。
9. 产物名预览对两个操作都出现，且与实际落盘一致。
10. 两个操作都能取消，取消后不留 `.part`、也不留 concat 列表文件。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 编码不一致时静默产出坏文件 | `check` 主动判 + 端到端拒绝测试（第 2 节的 174 行错误就是它） |
| 裁剪越界/奇数被 ffmpeg 静默改掉 | 我们判；界面让非法状态难以进入；配越界与奇数的拒绝测试 |
| 合并列表的路径转义漏了 | **复用** `escape_concat_path`，配撇号路径的回归测试 |
| 输入改成 Vec 会碰到现有三个操作 | 各传一个元素的 vec，行为不变；全量套件是安全网 |
| `JobContext` 的签名改动面大 | 五个能力集中在一个 impl 上，编译器会逐个指出调用点 |
| 进度条在合并时提前走满 | duration 取各段之和；端到端测试断言最终进度为 1.0 |
| 预览帧把主线程卡住 | 抽帧是一次 `ffmpeg -ss` 的单帧解码（几十毫秒），且只在文件/时间变化时跑 |

## 12. 非目标（YAGNI）

- 混源拼接的自动重编码（拒绝并指路去「转码」；这是刻意的，见 §5.2）
- 合并的拖拽排序
- 裁剪的鼠标拖拽框（本轮是数字输入 + 实时叠加框）
- 裁剪的时间轴拖拽预览（一帧足够）
- 合并的交叉淡化/转场
- 裁剪的旋转/翻转/缩放（那属于"调整尺寸"，是另一件事）
- 预览帧的多分辨率缓存
