# EasyDownVideo · 视频操作设计

- 日期：2026-10-16
- 状态：待评审
- 前置：`docs/superpowers/specs/2026-10-15-tauri-gui-design.md`（分层与事件桥仍然有效）
- 定位：新增「视频操作」子系统。**本轮只把通路立起来**，五个操作里只有「压缩」端到端可用

## 1. 背景与目标

界面里一直挂着一个「视频操作」入口，点进去是一句话占位。占位页的注释写着骨架按
「选文件 → 选操作 → 队列」预留，并明确留了一句："明确不做胜过一个假装能用、点了没反应的界面"。
本设计就是把它兑现。

**目标**：让人不必开终端，在应用里对本地视频做常见处理。本轮打通
**选文件 → 调参数 → 排队 → 看进度 → 可取消 → 产物落盘** 这条完整通路，
并且只用一个操作（压缩）把它走通 —— 其余四个照同一套长，不在本轮实现。

**为什么先压缩**：它是单文件输入（输入界面最简单）、耗时足够长（进度/取消能被真实验证）、
参数面典型（编码器 + 质量档位）。而且它和「转码」是同一条重编码通路，打通后转码几乎只换参数界面。

**成功标准**：拿一个真实视频点「压缩 · 均衡」，队列里出现一行、进度条真的在走、产物能播、
点取消能真的停下且不留下半截文件；另外四项在侧边栏可见但明确显示为不可用。

## 2. 家底与实测结论

这些是设计开始前实测的，不是推测。实施时可以直接采信，但**改动 ffmpeg 版本后需要重验**。

**内嵌 ffmpeg 是完整版**：`vendor/ffmpeg/macos-aarch64/ffmpeg` 是 9.0.2，含
`libx264`、`libx265`、`libsvtav1`、`libvpx`/`libvpx-vp9`，以及硬件编码器
`h264_videotoolbox`、`hevc_videotoolbox`、`prores_videotoolbox`。所以重编码不是"能不能做"的问题。

**没有 ffprobe。** `vendor/ffmpeg/` 下只有 ffmpeg 一个二进制。时长只能这么拿：

```
$ ffmpeg -i src.mp4 2>&1 | grep Duration
  Duration: 00:00:05.00, start: 0.000000, bitrate: 55 kb/s
```

（不带输出文件时 ffmpeg 以非零码退出，这是正常的 —— 我们要的是它打在 stderr 上的那行信息。）

**进度取自 `-progress pipe:1`**，它在 stdout 上按固定间隔吐键值对，与 stderr 的错误信息互不干扰：

```
out_time_us=4933333
out_time_ms=4933333
out_time=00:00:04.933333
progress=end
```

**`out_time_ms` 也是微秒。** 这是个老坑：两个字段名一个说 us 一个说 ms，实测 5 秒的片子两者都给出
4933333。照字面把 `out_time_ms` 当毫秒用，进度会永远停在 0.5%，而且**看起来像卡死**而不是像报错。

**VideoToolbox 会静默忽略 `-crf`。** 同一段 5 秒片：

| 命令 | 产物 |
|---|---|
| `-c:v h264_videotoolbox -crf 18` | 361026 字节 |
| `-c:v h264_videotoolbox -crf 40` | 361026 字节（**逐字节相同**） |
| `-c:v h264_videotoolbox -q:v 20` | 71206 字节 |
| `-c:v h264_videotoolbox -q:v 85` | 277140 字节 |
| `-c:v libx264 -crf 28`（对照） | 28634 字节 |

也就是说：**把编码器换个名字而保留 `-crf`，用户选「硬件」会得到一个比源文件还大、且全程不报错的产物。**
硬件编码器真正的质量旋钮是 `-q:v`，方向还与 CRF 相反（越大越清晰）。

## 3. 范围

**本轮做**：导航改造、`videoops` 子系统、压缩（三档 + 高级项）、输出与命名、取消、错误呈现，
以及上面那套测试。

**本轮不做**（在侧边栏照实列出并灰显，不做点击无反应的假按钮）：转码、合并、裁剪视频（截时间段）、
画面裁剪。它们共用本轮立起来的通路，之后逐个加。

**不做暂停**：ffmpeg 不支持断点续传，"暂停"只能靠 `SIGSTOP`/`SIGCONT` 冻住进程，跨平台不一致。
本轮只提供取消。**按钮也不放上去** —— 一个按下去不知道会发生什么的按钮比没有更糟。

## 4. 导航与页面结构

`Page` 从字符串联合改成带参数的形式（`ui/src/components/Sidebar.tsx`）：

```ts
export type VideoOp = "compress" | "transcode" | "merge" | "trim" | "crop";
export type Page =
  | { kind: "download" }
  | { kind: "settings" }
  | { kind: "videoOp"; op: VideoOp };
```

「视频操作」变成可展开的一组（disclosure）：

```
下载
视频操作              ▾
    压缩                 ← 本轮唯一可点
    转码       ┐
    合并       │ 灰显，悬停提示「还没做」，aria-disabled
    裁剪视频   │
    画面裁剪   ┘
设置
```

- **点「视频操作」本身只展开/收起，不导航。** 反馈就是子菜单展开；不把"当前在哪一页"和
  "展开没展开"两件事绑在一起。
- 展开状态放 `App` 的 state 里。理由与已有的 `url` 完全相同：三个页面是条件渲染的，
  切页会卸载整棵子树，状态放 `Sidebar` 内部的话一切页就重置（`App.tsx` 里那段注释记的
  就是这个回退）。
- 标题按页算：`videoOp` 显示该操作名（"压缩"），沿用 `App.tsx` 的 `TITLES` 位置。

## 5. Rust 侧：`videoops` 子系统

### 5.1 模块划分

`src/core/videoops/`：

| 文件 | 职责 |
|---|---|
| `mod.rs` | `VideoOps`：任务表、队列、并发、状态推进、对外命令入口 |
| `ffmpeg_job.rs` | 跑一次 ffmpeg：spawn、`-progress` 解析、取消、半截产物清理 |
| `media_info.rs` | `media_duration()`：解析 `ffmpeg -i` 的 stderr 拿时长 |
| `presets.rs` | 三档预设 + 高级项 → ffmpeg 参数。**纯函数**，是主要测试面 |

### 5.2 数据模型与状态机

```rust
pub type JobId = u64;

pub enum JobState {
    Queued,
    Running,
    Done,
    Failed(String),
    Canceled,
}

pub struct JobSnapshot {
    pub id: JobId,
    pub label: String,          // "压缩 · 均衡"，列表直接显示
    pub input: PathBuf,
    pub output: PathBuf,
    pub state: JobState,
    pub progress: Option<f64>,  // 0.0–1.0；时长拿不到时为 None
}
```

```
Queued ──起 worker──> Running ──> Done
   │                     ├──────> Failed(stderr 尾部)
   └──(取消未开始的)─────┴──────> Canceled（并删掉半截产物）
```

`progress` 用 `Option<f64>` 而不是复用下载那边的 `ProgressHandle`：后者按"字节/分片"计数，
而转码的自然单位是百分比，两边的量纲没有共用之处，硬套只会让两边都别扭。时长拿不到时给
`None`，界面显示不确定态进度条，**不编一个假分数**。

### 5.3 队列与并发

独立队列，并发上限**写死 1**。转码吃满 CPU，不该与下载抢 `max_active_tasks`；写死而不是做成
设置项是 YAGNI —— 以后真要放开，加一个设置项即可。

`pump()` 的结构与下载引擎同构（启动队列头部、worker 退出时再 pump 一次）。

### 5.4 事件与接线

新增 `VideoOpEvent { Added{id}, StateChanged{id, state}, Progress{id, fraction}, Removed{id} }`，
走**自己的 broadcast 通道**（容量 256，与下载一致）。

`bridge::run` 泛化：它现在是写死 `broadcast::Receiver<EngineEvent>` + `event_dto` 的，改成接受
一个"把事件映射成 JSON"的函数，于是它变成一根通用管道。**这样桥仍然只有一份实现** ——
`Lagged → 排空残余 → 发 resync` 那套推理（连同它防的那个"旧事件盖掉新快照、那一行永久停在错误
状态"的缺陷）不会被复制到第二处。`main.rs` 里多 spawn 一次即可。

下载事件的枚举**一个字都不用改**。

RESYNC 仍是同一个事件名：任一条通道落后，前端都整体重取（下载任务 + 视频任务）。宁可多取一次，
也不要漏。

### 5.5 命令面

新增六条，注册进 `main.rs` 的 `invoke_handler!`，并在 `ui/src/lib/ipc.ts` 里镜像：

| 命令 | 说明 |
|---|---|
| `add_compress_job(input, preset, advanced) -> JobId` | 入队前先校验输入文件存在可读 |
| `get_video_jobs() -> Vec<JobSnapshotDto>` | 全量，供水合与重同步 |
| `cancel_video_job(id)` | |
| `remove_video_job(id)` | 只对终态生效，与下载那边同规则 |
| `pick_video_file() -> Option<String>` | 走 `tauri-plugin-dialog` 的 `pick_file` |
| `probe_video(path) -> VideoInfoDto` | 时长/分辨率/码率，界面显示"源文件 1.2 GB · 12:34" |

`AppState` 增加一个 `videoops: VideoOps` 字段。`VideoOps` 与下载引擎共用同一个 tokio runtime handle
与 `data_dir`（后者用来解出内嵌 ffmpeg，复用已有的 `ensure_ffmpeg`）。

## 6. 压缩的行为

### 6.1 三档预设

分辨率一律不动 —— 压缩的语义是"同样的画面、更小的体积"，改画面尺寸是另一件事。

| 档位 | x264 `-crf` | VT `-q:v` | 音频 |
|---|---|---|---|
| 小体积 | 28 | 38 | aac 96k |
| 均衡（默认） | 24 | 52 | aac 128k |
| 高画质 | 20 | 60 | aac 192k |

VT 那三个数是**实测校准过的**（Task 1 Step 5）。素材为 10 秒 1280x720@30 的 `testsrc2`
加 440Hz 正弦；判据是同档 VT 与 x264 的体积比落在 0.8–1.5，且任意一档都不得大于源文件。
实测比值 1.05 / 1.04 / 0.99，三档 VT 产物（1.96/3.24/4.56 MB）都小于源文件（6.10 MB）。

**按刻度均匀内插出来的 50/65/80 是错的**：那三个值给出 1.56/1.70/1.96 倍，高画质一档
产出 9.0 MB —— 比源文件还大 48%。硬件编码器在同等感知质量下本就比 x264 占地方，
所以同一档的 `q:v` 必须更低。校准数据记在 `presets.rs` 的 `preset_defaults` 文档注释里。

### 6.2 质量旋钮必须显式分流

CRF 越小越清晰，`-q:v` 越大越清晰 —— 方向相反，且 VideoToolbox 对 `-crf` 是**静默忽略**的。
所以参数构造里必须是两条明确的路径，绝不允许"换个编码器、质量参数照旧"这种写法：

```rust
match encoder {
    Encoder::X264 => { cmd.arg("-crf").arg(crf); }
    Encoder::VideoToolbox => { cmd.arg("-q:v").arg(qv); }
}
```

### 6.3 高级项

- **编码器**：自动 / 硬件 / 软件。**「自动」= 软件 x264** —— 体积画质比最好且可预测。
  硬件是给"要快"的人显式开的选项，不默认启用（默认硬件等于默认降质）。
- **分辨率**：保持原样 / 1080p / 720p（`scale=-2:1080`，保宽高比、宽取偶数）。
- **质量微调**：软件编码下是 CRF（范围 14–32：低于 14 体积暴涨而肉眼几乎无差别，
  高于 32 画质开始明显劣化），硬件编码下换成 `-q:v`（范围 20–90）。**两者的滑杆方向相反**，
  界面文案要说清哪头是"更小体积"，不能只画一根没有标签的滑杆。

容器固定 mp4（我们重编码成 h264+aac，mp4 一定装得下），本轮不给选项。

### 6.4 输出与命名

- 落到设置里的下载目录，操作页可临时改。
- 命名 `<原名>-压缩.mp4`；重名让路成 ` (1)`、` (2)` —— 复用下载那边的
  `unique_path_avoiding`，与仓库既有约定保持一致（不另创一套后缀风格）。
  **源文件绝不会被覆盖**。
- 产物先写 `<目标名>.part`，成功后 `rename` 过去 —— 与 HLS 分片同样的理由：直接写目标名的话，
  中途被杀会留下一个半截文件，而"文件存在"就会被当成完成。`rename` 在同一文件系统内是原子的，
  所以"改过名"就等价于"完整"。

### 6.5 命令行构造的其余要点

`-nostdin`（不让 ffmpeg 去读 stdin）、`-hide_banner`、`-progress pipe:1`、`-y`、
`kill_on_drop(true)`（照抄 `build_remux` 的理由：否则取消后它变成孤儿进程继续写）。

## 7. 错误处理

- ffmpeg 非零退出 → `Failed(错误摘要)`。摘要取 stderr 的**最后 20 行、且总长不超过 2 KB**
  （超出则从头丢弃）—— ffmpeg 的错误总在尾部，而它跑一个长任务能动辄吐出几千行进度噪声。
- 失败或取消 → **删掉半截产物**。这是 `remux_to_mp4` 已经踩过的坑：留在盘上会让用户看到
  一个打不开的 mp4，而任务显示"已取消"。
- 取消的收尾顺序照抄 `remux_to_mp4`：**先 kill、再等它真的退出、最后才删产物**。顺序反了的话，
  进程还有一次写在做，删完它会把半截文件重新写出来。
- 输入文件不存在/不可读 → 在 `add_compress_job` 就报错，不排进队列之后再失败。
- 时长拿不到（文件损坏等）→ 不阻断任务，进度退化为不确定态。

## 8. 测试策略

| 层 | 内容 |
|---|---|
| `presets.rs` 纯函数 | 三档 → 参数向量，断言 CRF/`-q:v`/音频码率/编码器；**专门一条**断言选硬件时出现 `-q:v` 且**不出现** `-crf`（这是第 2 节那个静默忽略的回归测试） |
| 时长解析 | 喂真实 stderr 片段（含 `Duration: 00:00:05.00`）断言解析结果；坏输入返回 `None` 而不 panic |
| 进度解析 | 喂真实 `-progress` 行，断言 5 秒片子给 4.93/5.0；**专门一条**钉住 `out_time_ms` 按微秒解释 |
| 命名 | `<原名>-压缩.mp4`；已存在时让路成 `-2`；输入与输出同名时不得覆盖源文件 |
| **端到端真跑** | 用内嵌 ffmpeg 造一段 5 秒合成片 → 真跑一次压缩 → 断言产物存在、比源小、能被 ffmpeg 读回且时长≈5 秒 |
| 取消 | 起一个真实的长任务，取消 → 断言子进程已退出、半截产物已被删除 |

端到端那条**不需要网络**（ffmpeg 是内嵌的、素材是现造的），可以进常规测试套件 —— 这是本设计里
最强的验证，能让 5.2 那类"静默走错路"的问题在 CI 就暴露。

界面侧沿用现有做法：纯逻辑抽成 `ui/src/lib/` 下的模块并配 vitest（本轮预计是"操作 → 标题/文案"
这类映射），组件本身不做 DOM 测试。

## 9. 验收清单（手动，逐项过）

1. 侧边栏点「视频操作」→ 展开子菜单；再点一下 → 收起。切到别的页再切回来，展开状态还在。
2. 未实现的四项灰显，悬停有「还没做」提示，点了不发生任何导航。
3. 点「压缩」→ 页面标题变「压缩」，有选文件入口。
4. 选一个真实视频 → 显示源文件信息（体积、时长）。
5. 三档预设可切换；展开「高级」能看到编码器/分辨率/CRF。
6. 点开始 → 任务出现在列表，进度条**真的在走**（不是 0% 卡住，也不是瞬间 100%）。
7. 产物落在下载目录，能正常播放，体积确实变小。
8. 再来一次同名任务 → 产物自动让路成 `-2`，源文件未被改动。
9. 起一个长任务 → 点取消 → 很快停下，产物目录里没有残留半截文件。
10. 输入一个损坏/不可读的文件 → 立即报错，不排进队列。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 硬件编码器静默忽略质量参数 | 5.2 已实测；参数构造分两条路径，并有一条专门的回归测试 |
| `out_time_ms` 单位误用导致进度像卡死 | 已实测；进度解析有专门测试钉住微秒解释 |
| 画质档位的数值拍脑袋 | 5.1 的 VT 三个值标为待校准，实施计划里排了校准步骤 |
| 动到 `bridge.rs` 影响下载通路 | 只做泛化、不改语义；下载事件的枚举与 DTO 完全不动；桥的既有测试继续跑 |
| 转码把界面卡住（CPU 吃满 / 进度事件太密） | 并发写死 1；进度按 ffmpeg 自己的间隔（约 0.5s）转发，不额外加频 |

## 11. 非目标（YAGNI）

- 转码/合并/裁剪视频/画面裁剪（本轮只立通路）
- 暂停与断点续传（ffmpeg 不支持，见第 3 节）
- 批量：一次选多个文件排成多个任务（先一对一，界面简单）
- 容器格式选择（固定 mp4）
- 转码预设的记忆与用户自定义预设
- 视频预览播放器
- 硬件编码器的自动回退（选了硬件但机器不支持时的降级策略）
